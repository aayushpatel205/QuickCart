# QuickCart – Payment Service: Report Paragraph

## Design Pattern Implementation Summary

### ACID Transactions
Payment creation and refunds are each executed within a single SQLAlchemy database transaction (`BEGIN … COMMIT`). In `payment_service.py`, `process_payment()` writes the `Payment` row and flushes it within the session context provided by the FastAPI `get_db` dependency; only when the entire handler returns successfully does the session auto-commit. Similarly, `process_refund()` atomically updates the payment status to `REFUNDED`. If any step fails, the transaction is rolled back, ensuring the database never contains a partial record. The Kafka consumer additionally writes both the payment row and the `ProcessedEvent` deduplication record in the **same** database transaction before committing the Kafka offset, guaranteeing that either both succeed or neither does.

### Idempotency
Idempotency is enforced at two levels. At the **REST layer**, the `payments` table has a `UNIQUE` constraint on both `order_id` and `idempotency_key`; a repeated `POST /payments/pay` with the same `idempotencyKey` returns the already-existing row without calling the gateway again. A pre-check query detects the duplicate before attempting an insert, and an `IntegrityError` catch handles the race-condition case of concurrent requests. At the **Kafka consumer layer**, every consumed message is identified by its `partition:offset` string, stored in the `processed_events` table within the same DB transaction as the payment write. Before processing any event, the consumer checks this table and skips the message if it has already been handled—protecting against Kafka's at-least-once redelivery guarantee and consumer group rebalances.

### Circuit Breaker & Resilience
The simulated external payment-gateway call in `circuit_breaker.py` is wrapped with a **pybreaker** circuit breaker (`CircuitBreaker(fail_max=5, reset_timeout=60)`). After 5 consecutive failures the circuit opens and subsequent calls fail immediately with `CircuitBreakerError`, preventing cascading load on the (simulated) downstream system. Transient `GatewayError` exceptions are retried up to three times with **tenacity** exponential backoff (0.5 s initial, doubling each attempt, capped at 4 s). When the circuit is open, the payment handler catches `CircuitBreakerError` and publishes `payment.failed` with reason `"gateway unavailable"`, ensuring the order-service receives a definitive result and can mark the order as cancelled.

### Event-Driven Communication
The service participates in the QuickCart Kafka event bus as both consumer and producer. It subscribes to the `order.created` topic under the consumer group `payment-service` and, after processing, publishes either `payment.completed` or `payment.failed` to the corresponding topics. Manual offset commits (enabled via `enable_auto_commit=False`) ensure offsets advance only after successful DB writes, preventing silent message loss on crashes. Events include `orderId`, `timestamp`, and `correlationId` to support distributed tracing across services.

### Monitoring
The service exposes a Prometheus-compatible `/metrics` endpoint via the `prometheus-client` library. Two custom metrics instrument payment-specific behaviour: `payments_total{status}` (a counter tracking completed, failed, and refunded payments) and `payment_latency_seconds` (a histogram recording end-to-end gateway call latency with eight buckets from 50 ms to 10 s). Generic HTTP metrics (`http_requests_total`, `http_request_duration_seconds`) are collected by an ASGI middleware on every request. A centralised Prometheus instance scrapes all five QuickCart services plus Kong and the Kafka exporter every 15 seconds. A pre-provisioned Grafana dashboard visualises requests per second per service, error rates, P95 latency across services, and the payments-completed vs payments-failed time series. Alert rules fire on service downtime (1-minute absence), error rates above 5 %, payment failure spikes above 20 %, and P95 latency exceeding 2 seconds.
